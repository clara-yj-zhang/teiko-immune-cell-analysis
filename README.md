# teiko-immune-cell-analysis
An end-to-end data project that loads raw immune cell count data, stores it in a SQLite database, performs clinical trial response analysis, and presents the results in an interactive dashboard.

## How to Run (GitHub Codespaces)

1. **Open in Codespaces** — click the green **Code** button on GitHub → **Codespaces** → **Create codespace on main**.

2. **Install dependencies:**
   ```bash
   make setup
   ```

3. **Run the full data pipeline** (creates the database, loads all data, generates frequency tables and all output plots):
   ```bash
   make pipeline
   ```

4. **Launch the interactive dashboard:**
   ```bash
   make dashboard
   ```
   Codespaces will pop up a prompt to open the forwarded port — click **Open in Browser**. The dashboard runs on http://localhost:8501.


### Requirements
- Python 3.9+
- All Python dependencies are listed in `requirements.txt` and installed by `make setup`.
- No external database server needed — SQLite is part of the Python standard library.

## Code Structure

```
teiko-immune-cell-analysis/
├── load_data.py        # Part 1 — initializes SQLite DB and loads cell-count.csv
├── analysis.py         # Parts 2–4 — frequency table, statistical analysis, subset queries
├── dashboard.py        # Interactive Streamlit dashboard for all parts
├── cell-count.csv      # Raw input data
├── immune_cells.db     # SQLite database (generated by make pipeline)
├── outputs/            # PNG boxplots (generated by make pipeline)
│   ├── boxplot_responders_day0.png
│   ├── boxplot_responders_day7.png
│   └── boxplot_responders_day14.png
├── requirements.txt    # Python dependencies
├── Makefile            # make setup / make pipeline / make dashboard
└── README.md
```

The project is split into three layers with a clear separation of concerns:

- **`load_data.py`** — data ingestion only. Self-contained with no imports from the rest of the project, so the database can be rebuilt at any time without touching analysis code. Handles deduplication of subjects and treatment enrollments on load.
- **`analysis.py`** — all business logic. Exposes each analytical result (frequency table, significance tests, subset queries) as a plain Python function returning a DataFrame. A `__main__` block runs the full pipeline headlessly, so `make pipeline` works without a browser.
- **`dashboard.py`** — UI only. Calls functions from `analysis.py` and renders results interactively. Contains no query logic of its own — this means the same analysis is reproducible with or without the dashboard.

## Database Schema

Three normalized tables: `subjects` → `treatments` → `samples`.

### `subjects`
| Field | Type | Description |
|---|---|---|
| `subject` | TEXT (PK) | Unique patient identifier (e.g. `sbj000`) |
| `project` | TEXT | Study/trial the subject belongs to (e.g. `prj1`) |
| `condition` | TEXT | Disease condition: `melanoma`, `carcinoma`, or `healthy` |
| `age` | INTEGER | Patient age in years |
| `sex` | TEXT | Patient sex: `M` or `F` |

### `treatments`
| Field | Type | Description |
|---|---|---|
| `id` | INTEGER (PK) | Auto-assigned enrollment ID |
| `subject` | TEXT (FK → subjects) | The subject receiving this treatment |
| `treatment` | TEXT | Drug administered: `miraclib`, `phauximab`, or `none` |
| `response` | TEXT | Whether the subject responded: `yes`, `no`, or `NULL` (healthy/untreated) |

### `samples`
| Field | Type | Description |
|---|---|---|
| `sample` | TEXT (PK) | Unique sample identifier (e.g. `sample00000`) |
| `treatment_id` | INTEGER (FK → treatments) | The treatment enrollment this sample was collected under |
| `sample_type` | TEXT | Type of biological sample: `PBMC` (Peripheral Blood Mononuclear Cells) or `WB` (Whole Blood) |
| `time_from_treatment_start` | INTEGER | Days since treatment started: `0`, `7`, or `14` |
| `b_cell` | INTEGER | B cell count |
| `cd8_t_cell` | INTEGER | CD8+ cytotoxic T cell count |
| `cd4_t_cell` | INTEGER | CD4+ helper T cell count |
| `nk_cell` | INTEGER | Natural Killer cell count |
| `monocyte` | INTEGER | Monocyte count |

### Design Rationale & Scalability

The schema is organized around one guiding principle: **each fact lives at the level it naturally belongs to** — the person, the treatment enrollment, or the individual sample.

**`subjects`** stores immutable patient demographics. `project` lives here because it is a subject-level fact — a patient belongs to one study regardless of how many samples they contribute.

**`treatments`** stores each treatment enrollment as its own row. `treatment` and `response` are enrollment-level facts: a patient might receive more than one drug across a trial. Separating this table means a new enrollment is just a new row — no schema change, no risk of inconsistent `response` values spread across sample rows.

**`samples`** stores each individual blood draw, linked to a treatment enrollment. `time_from_treatment_start` lives here because it describes *when the sample was taken*, not who the patient is or which drug they received.

**Scalability:** With hundreds of projects and thousands of samples, this design holds up well:
- All cross-project or cross-condition queries are simple `JOIN`s — no denormalization needed.
- Adding new projects, subjects, or samples requires only `INSERT` statements; no columns change.
- The `sample_details` view pre-joins all three tables so analytical queries remain one-liners.
- If projects grow their own metadata (phase, start date, PI), `project` can be promoted to its own table with a FK on `subjects` — a non-breaking migration.
- If new cell populations are measured, they can be added as new columns on `samples`, or the table can be refactored to a long format (`cell_counts(sample, population, count)`) to make population additions schema-free. The long format also enables population-agnostic aggregation queries without hardcoding column names.

### Statistical Analysis Design (Part 3)

The comparison of responders vs non-responders uses **one observation per subject at a selected time point**, not one observation per sample. This is a deliberate statistical design choice:

- Each subject contributes 3 samples (day 0, 7, 14). These samples are **not independent** — they come from the same patient. Treating all 3 as separate data points in a Mann-Whitney U test would inflate the effective sample size and violate the independence assumption, risking falsely significant p-values.
- By filtering to a single time point, each subject contributes exactly one data point, satisfying the independence requirement.
- The time point is kept as a user-selectable parameter (not fixed to baseline) because immune cell dynamics differ across the treatment course — a population may only diverge between responders and non-responders at a later time point (e.g., day 14), which would be missed if analysis were restricted to baseline alone.
- **Note vs spec:** The project description does not explicitly restrict to a single time point — it says to use "the data reported in the summary table" (all samples). Filtering per time point is a deliberate statistical improvement to ensure independence of observations. The dashboard exposes all time points so the full picture is available, and the saved PNG outputs cover all three time points.
- **Mann-Whitney U** (non-parametric) was chosen over a t-test because cell population percentages are not guaranteed to follow a normal distribution, especially in small clinical trial cohorts.

### Future Extensions

**`project` as its own table:** Currently `project` is stored as a plain text field on `subjects`. As the database grows, projects will likely have their own metadata (e.g. trial phase, start date, lead researcher, target indication). At that point, `project` should be extracted into a dedicated table:

```
projects(project PK, phase, start_date, ...)
subjects(subject PK, project FK → projects, condition, age, sex)
```

This follows the same normalization principle used throughout this schema — facts about a project belong to the project, not repeated on every subject row.

**Normalize cell counts into rows:** Currently the five cell populations are stored as fixed columns (`b_cell`, `cd8_t_cell`, etc.) in `samples`. A fully normalized alternative would store them as rows:

```
cell_counts(id PK, sample FK, population TEXT, count INTEGER)
```

This makes adding new cell populations schema-free (insert rows, no `ALTER TABLE`), and simplifies aggregate queries like total count per sample. The tradeoff is that retrieving a wide format (one column per population) requires a pivot. This refactor is worthwhile once the set of measured populations becomes dynamic.

**Data validation and cleaning in `load_data.py`:** Currently the loader assumes the CSV is well-formed. In a production pipeline, `load_data.py` should be extended to handle:
- Stripping leading/trailing whitespace from string fields
- Validating expected value sets (e.g. `condition`, `treatment`) and logging or rejecting unrecognized values
- Checking for missing or null values in required fields
- Reporting malformed rows with line numbers instead of crashing silently
